# Claude Code Agent Teams 가이드

> 원본 문서: https://code.claude.com/docs/en/agent-teams
> 작성일: 2026-04-10

> ⚠️ **실험적 기능**: Agent Teams는 실험 기능이며 기본적으로 비활성화되어 있습니다. 사용하려면 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 환경변수를 설정해야 하고, Claude Code v2.1.32 이상이 필요합니다. (`claude --version` 으로 확인)

---

## 1. Agent Teams란?

Agent Teams는 **여러 Claude Code 인스턴스를 하나의 팀처럼 운영**하는 기능입니다.

- 하나의 세션이 **팀 리드(Team Lead)** 가 되어 작업을 조율, 할당, 결과를 취합합니다.
- 각 **팀메이트(Teammate)** 는 자신만의 컨텍스트 창에서 독립적으로 작업합니다.
- 팀메이트들은 **서로 직접 메시지를 주고받으며** 협업합니다.
- 사용자는 리드뿐 아니라 **개별 팀메이트와도 직접 대화**할 수 있습니다.

### Subagents와의 차이

| 항목 | Subagents | Agent Teams |
|------|-----------|-------------|
| **컨텍스트** | 독립 컨텍스트, 결과만 호출자에게 반환 | 독립 컨텍스트, 완전 독립 세션 |
| **통신** | 메인 에이전트에게만 결과 보고 | 팀메이트끼리 직접 메시지 교환 |
| **조율** | 메인 에이전트가 모든 작업 관리 | 공유 작업 리스트 기반 자가 조율 |
| **적합한 작업** | 결과만 필요한 집중형 작업 | 토론·협업이 필요한 복잡한 작업 |
| **토큰 비용** | 낮음 (결과만 메인에 요약) | 높음 (각 팀메이트가 독립 인스턴스) |

**결론**: 단순히 결과만 받으면 되는 병렬 작업은 Subagents, 팀원끼리 의견을 주고받으며 협업해야 하는 작업은 Agent Teams를 사용합니다.

## 2. 언제 사용하는가?

### 적합한 사용 사례

- **리서치와 리뷰**: 여러 팀메이트가 문제의 다른 측면을 동시에 조사하고 서로 검증
- **신규 모듈/기능 개발**: 각 팀메이트가 서로 간섭 없이 독립된 부분을 담당
- **경쟁 가설 기반 디버깅**: 서로 다른 가설을 병렬로 검증해 빠르게 원인 수렴
- **계층 간 협업**: 프론트엔드, 백엔드, 테스트를 각각 담당하는 팀원끼리 조율

### 부적합한 경우

- 순차적 작업 (이전 결과에 의존)
- 같은 파일을 편집해야 하는 작업 (충돌 발생)
- 단순 반복 작업
- 종속성이 많은 작업

→ 이런 경우에는 **단일 세션**이나 **Subagents**가 더 효과적입니다.

## 3. 활성화 방법

### 환경변수 설정

`settings.json` 또는 쉘 환경변수로 설정합니다.

**이 프로젝트에는 이미 `.claude/settings.json`에 설정되어 있습니다:**

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

설정 후 **Claude Code를 재시작**해야 적용됩니다.

## 4. 첫 번째 팀 만들기

자연어로 리드에게 팀 구성과 작업을 설명하면 됩니다.

### 예시 프롬프트

```text
개발자가 코드베이스 내의 TODO 주석을 추적할 수 있는 CLI 도구를 설계하고 있습니다.
이 문제를 다양한 관점에서 탐색할 agent team을 만들어주세요:
한 명은 UX, 한 명은 기술 아키텍처, 한 명은 악마의 변호인(devil's advocate) 역할.
```

리드는 자동으로:
1. 공유 작업 리스트를 생성
2. 각 관점별 팀메이트를 스폰
3. 팀메이트들이 문제를 탐색하도록 지시
4. 결과를 취합
5. 완료 후 팀을 정리

## 5. 팀 제어하기

### 5.1 디스플레이 모드

Agent Teams는 두 가지 디스플레이 모드를 지원합니다.

| 모드 | 설명 | 요구사항 |
|------|------|----------|
| **In-process** | 모든 팀메이트가 메인 터미널 안에서 실행. Shift+Down으로 순환하며 메시지 전송 | 없음 (모든 터미널에서 동작) |
| **Split panes** | 각 팀메이트가 별도 분할 창에 표시. 동시에 모든 출력 확인 가능 | tmux 또는 iTerm2 |

기본값은 `"auto"` — tmux 세션 안이면 분할 창, 아니면 in-process 모드.

`~/.claude.json` (글로벌 설정)에서 변경:

```json
{
  "teammateMode": "in-process"
}
```

단일 세션에만 강제 적용:

```bash
claude --teammate-mode in-process
```

**Windows 환경 주의**: 분할 창 모드(`tmux`)는 macOS에서 가장 잘 동작합니다. Windows 환경에서는 **in-process 모드 사용을 권장**합니다. VS Code 통합 터미널, Windows Terminal, Ghostty는 분할 창 모드를 지원하지 않습니다.

### 5.2 팀메이트 수와 모델 지정

리드가 자동으로 결정하게 두거나 명시적으로 요청할 수 있습니다.

```text
4명의 팀메이트로 팀을 구성해서 이 모듈들을 병렬로 리팩토링해주세요.
각 팀메이트는 Sonnet을 사용하세요.
```

### 5.3 팀메이트 계획 승인 요구

복잡하거나 위험한 작업은 **plan mode**를 강제할 수 있습니다. 팀메이트는 읽기 전용 모드로 계획을 세우고, 리드가 승인해야 구현을 시작합니다.

```text
authentication 모듈을 리팩토링할 architect 팀메이트를 스폰하세요.
변경 작업 전에 계획 승인을 반드시 요구하세요.
```

리드의 승인 기준에 영향을 주려면 프롬프트에 명시합니다:
- "테스트 커버리지가 포함된 계획만 승인해"
- "DB 스키마를 수정하는 계획은 거부해"

### 5.4 팀메이트와 직접 대화

각 팀메이트는 독립된 전체 Claude Code 세션입니다.

- **In-process 모드**:
  - `Shift+Down`: 팀메이트 순환
  - 타이핑 후 전송: 직접 메시지 보내기
  - `Enter`: 팀메이트 세션 보기
  - `Escape`: 현재 턴 중단
  - `Ctrl+T`: 작업 리스트 토글
- **Split-pane 모드**: 해당 pane을 클릭해 직접 상호작용

### 5.5 작업 할당과 클레임

공유 작업 리스트를 통해 조율됩니다.

- 작업 상태: **pending → in progress → completed**
- 종속성 지원: 선행 작업이 완료되지 않으면 클레임 불가
- 리드가 명시적으로 할당하거나 팀메이트가 스스로 다음 작업을 클레임
- 파일 락 기반으로 동시 클레임 경쟁 방지

### 5.6 팀메이트 종료

```text
researcher 팀메이트에게 종료를 요청하세요
```

리드가 종료 요청을 보내면 팀메이트는 승인하거나 이유와 함께 거부할 수 있습니다.

### 5.7 팀 정리 (Clean up)

작업이 끝나면 반드시 리드에게 정리를 요청해야 합니다.

```text
팀을 정리해주세요
```

> ⚠️ **주의**: 정리는 **반드시 리드를 통해** 해야 합니다. 팀메이트가 직접 정리하면 팀 컨텍스트가 제대로 해석되지 않아 리소스가 불일치 상태로 남을 수 있습니다. 또한 활성 팀메이트가 남아 있으면 정리가 실패하므로, 먼저 종료시킨 후 정리하세요.

### 5.8 Hooks로 품질 게이트 강제

- [`TeammateIdle`](https://code.claude.com/docs/en/hooks#teammateidle): 팀메이트가 idle로 전환되기 직전 실행. exit code 2로 피드백 후 계속 작업 유도
- [`TaskCreated`](https://code.claude.com/docs/en/hooks#taskcreated): 작업 생성 시 실행. exit code 2로 생성 차단
- [`TaskCompleted`](https://code.claude.com/docs/en/hooks#taskcompleted): 작업 완료 시 실행. exit code 2로 완료 차단

## 6. 동작 원리

### 6.1 구성 요소

| 구성 요소 | 역할 |
|-----------|------|
| **Team lead** | 팀을 생성, 팀메이트를 스폰, 작업을 조율하는 메인 세션 |
| **Teammates** | 할당된 작업을 수행하는 독립 Claude Code 인스턴스 |
| **Task list** | 팀메이트들이 클레임·완료하는 공유 작업 리스트 |
| **Mailbox** | 에이전트 간 메시지 교환 시스템 |

### 6.2 저장 위치

- **팀 설정**: `~/.claude/teams/{team-name}/config.json`
- **작업 리스트**: `~/.claude/tasks/{team-name}/`

두 파일은 팀 생성 시 자동으로 만들어지고 상태 변경 시 자동 업데이트됩니다. **직접 수정하지 마세요**. 다음 상태 업데이트 때 덮어써집니다.

team config의 `members` 배열에는 각 팀메이트의 이름, agent ID, agent 타입이 저장되어 있어 팀메이트들이 서로 검색할 수 있습니다.

> 프로젝트 레벨의 팀 설정은 없습니다. `.claude/teams/teams.json` 같은 파일은 인식되지 않고 일반 파일로 처리됩니다.

### 6.3 Subagent 정의 재사용

팀메이트 스폰 시 기존 [subagent](https://code.claude.com/docs/en/sub-agents) 타입을 참조할 수 있습니다 (project, user, plugin, CLI 스코프 모두 가능).

```text
auth 모듈을 감사할 security-reviewer agent 타입으로 팀메이트를 스폰해주세요.
```

- subagent 정의의 `tools` 허용 목록과 `model` 설정이 적용됨
- 정의 본문은 시스템 프롬프트에 **추가**됨 (교체가 아님)
- `SendMessage`, task 관리 도구는 `tools` 제한과 무관하게 항상 사용 가능

> 단, subagent 정의의 `skills`와 `mcpServers` frontmatter는 팀메이트 실행 시 적용되지 않습니다. 팀메이트는 일반 세션과 동일하게 프로젝트/사용자 설정에서 skills와 MCP 서버를 로드합니다.

### 6.4 권한

팀메이트는 리드의 권한 설정으로 시작합니다. 리드가 `--dangerously-skip-permissions`로 실행 중이면 모든 팀메이트도 동일합니다. 스폰 후 개별 팀메이트의 모드를 변경할 수는 있지만, **스폰 시점에 팀메이트별 모드를 설정할 수는 없습니다**.

### 6.5 컨텍스트와 통신

각 팀메이트는 독립 컨텍스트 창을 가지며, 스폰 시 일반 세션과 동일한 프로젝트 컨텍스트(CLAUDE.md, MCP 서버, skills)를 로드합니다. **리드의 대화 히스토리는 전달되지 않습니다**.

**정보 공유 방식:**
- **자동 메시지 전달**: 팀메이트가 보낸 메시지는 자동으로 수신자에게 전달됨 (리드가 폴링할 필요 없음)
- **Idle 알림**: 팀메이트가 작업을 마치고 idle 상태가 되면 자동으로 리드에게 알림
- **공유 작업 리스트**: 모든 에이전트가 작업 상태를 확인하고 가용 작업을 클레임 가능

**팀메이트 메시징:**
- `message`: 특정 팀메이트 1명에게 전송
- `broadcast`: 모든 팀메이트에게 동시 전송 (비용이 팀 크기에 비례하므로 아껴 사용)

리드는 스폰 시 팀메이트에게 이름을 부여하고, 팀메이트끼리는 이 이름으로 서로 메시지를 보냅니다. 예측 가능한 이름이 필요하면 스폰 지시에 원하는 이름을 명시하세요.

### 6.6 토큰 사용량

Agent teams는 단일 세션보다 **현저히 많은 토큰**을 사용합니다. 각 팀메이트가 독립 컨텍스트 창을 가지므로 팀메이트 수에 비례해 사용량이 증가합니다. 리서치, 리뷰, 신기능 개발에는 가치가 있지만 단순 반복 작업은 단일 세션이 더 경제적입니다.

## 7. 실전 사용 예시

### 7.1 병렬 코드 리뷰

```text
PR #142를 리뷰할 agent team을 만들어주세요. 3명의 리뷰어를 스폰하세요:
- 1명: 보안 영향에 집중
- 1명: 성능 영향 확인
- 1명: 테스트 커버리지 검증
각자 리뷰 후 findings를 보고하게 해주세요.
```

리드가 세 관점의 결과를 취합합니다.

### 7.2 경쟁 가설 조사 (디버깅)

```text
사용자들이 앱이 한 메시지 후 연결을 유지하지 못하고 종료된다고 보고합니다.
5명의 팀메이트를 스폰해 서로 다른 가설을 조사하게 하세요.
서로 대화하며 과학 토론처럼 상대의 이론을 반박하도록 하세요.
합의된 내용을 findings 문서에 기록하세요.
```

**포인트**: 순차 조사는 한 가설에 고착되는 anchoring 편향이 있습니다. 서로 반증하는 구조로 설계하면 살아남은 가설이 실제 원인일 가능성이 훨씬 높습니다.

## 8. 베스트 프랙티스

### 8.1 팀메이트에게 충분한 컨텍스트 제공

팀메이트는 CLAUDE.md, MCP 서버, skills는 자동 로드하지만 **리드의 대화 히스토리는 상속하지 않습니다**. 작업 특화 정보는 스폰 프롬프트에 명시하세요.

```text
security reviewer 팀메이트를 다음 프롬프트로 스폰하세요:
"src/auth/ 의 인증 모듈을 보안 취약점 관점에서 리뷰하세요.
토큰 처리, 세션 관리, 입력 검증에 집중하세요.
앱은 httpOnly 쿠키에 저장된 JWT 토큰을 사용합니다.
발견된 이슈를 심각도 등급과 함께 보고하세요."
```

### 8.2 적절한 팀 크기 선택

- **시작 권장**: 3~5명
- **토큰 비용은 선형 증가**: 팀메이트 수만큼 비용 증가
- **조율 오버헤드**: 팀원이 많을수록 커뮤니케이션·충돌 비용 증가
- **한계 효용 체감**: 일정 수 이상은 비례적인 속도 향상이 없음
- **작업/팀원 비율**: 팀메이트당 5~6개 작업이 효율적. 15개 독립 작업이면 3명으로 시작.

"집중된 3명이 산만한 5명보다 낫다"

### 8.3 작업 크기 조절

| 크기 | 문제 |
|------|------|
| 너무 작음 | 조율 오버헤드가 이득을 초과 |
| 너무 큼 | 체크인 없이 오래 작업해 낭비 위험 증가 |
| 적절 | 자체 완결된 단위 (함수, 테스트 파일, 리뷰 등) |

리드가 작업을 충분히 쪼개지 않으면 "작업을 더 작게 나눠달라"고 요청하세요.

### 8.4 팀메이트가 끝나기를 기다리게 하기

리드가 팀메이트에게 맡기지 않고 직접 작업을 시작하면:

```text
진행하기 전에 팀메이트들이 작업을 완료할 때까지 기다리세요
```

### 8.5 리서치와 리뷰로 시작

처음 사용한다면 **경계가 명확하고 코드를 작성하지 않는 작업**부터 시작하세요:
- PR 리뷰
- 라이브러리 리서치
- 버그 조사

병렬 구현이 주는 조율 난제 없이 병렬 탐색의 가치를 경험할 수 있습니다.

### 8.6 파일 충돌 방지

**두 팀메이트가 같은 파일을 편집하면 덮어쓰기가 발생**합니다. 각 팀메이트가 서로 다른 파일 세트를 담당하도록 작업을 분리하세요.

### 8.7 모니터링과 방향 조정

팀메이트 진행 상황을 주기적으로 체크하고, 잘못된 접근은 방향을 바꾸고, findings는 들어오는 대로 취합하세요. 오래 방치하면 낭비 위험이 커집니다.

## 9. 트러블슈팅

### 팀메이트가 보이지 않음
- In-process 모드에서는 이미 실행 중이지만 화면에 안 보일 수 있음 → `Shift+Down`으로 순환
- 작업이 팀을 만들 만큼 복잡한지 확인 (Claude가 판단)
- 분할 창 모드면 tmux 설치 확인: `which tmux`
- iTerm2면 `it2` CLI 설치와 Python API 활성화 확인

### 권한 프롬프트가 너무 많음
팀메이트의 권한 요청은 리드로 버블링됩니다. 스폰 전에 [permission settings](https://code.claude.com/docs/en/permissions)에서 흔한 작업을 사전 승인하세요.

### 팀메이트가 오류 후 멈춤
오류 후 복구하지 못하고 정지할 수 있습니다.
- `Shift+Down`(in-process) 또는 pane 클릭(split)으로 출력 확인
- 직접 추가 지시
- 또는 대체 팀메이트를 스폰

### 리드가 작업 완료 전에 종료
- "계속 진행해"라고 리드에 지시
- 위임 대신 직접 작업하면 "팀메이트가 끝날 때까지 기다려"라고 지시

### Orphaned tmux 세션
팀 종료 후에도 tmux 세션이 남으면 수동 종료:

```bash
tmux ls
tmux kill-session -t <session-name>
```

## 10. 현재 한계 (실험 단계)

- **In-process 팀메이트 세션 재개 불가**: `/resume`, `/rewind`로 복원되지 않음. 리드가 존재하지 않는 팀메이트에게 메시지 보내려 할 수 있음 → 새로 스폰 요청
- **작업 상태 지연**: 팀메이트가 완료 표시를 놓쳐 종속 작업이 막힐 수 있음 → 수동 업데이트 또는 리드에게 푸시 요청
- **종료가 느릴 수 있음**: 현재 요청/도구 호출 완료 후 종료
- **세션당 1개 팀**: 리드는 한 번에 하나의 팀만 관리. 새 팀 시작 전에 현재 팀 정리
- **중첩 팀 불가**: 팀메이트는 자체 팀이나 팀메이트를 스폰할 수 없음
- **리드 고정**: 팀을 만든 세션이 수명 내내 리드. 팀메이트를 리드로 승격하거나 이전 불가
- **권한은 스폰 시점에 결정**: 스폰 시점에 팀메이트별 모드 설정 불가. 스폰 후 개별 변경은 가능
- **분할 창은 tmux/iTerm2 필요**: VS Code 통합 터미널, Windows Terminal, Ghostty에서는 분할 창 모드 사용 불가

> 💡 **`CLAUDE.md`는 정상 동작**: 팀메이트는 작업 디렉터리의 `CLAUDE.md`를 읽습니다. 이를 활용해 모든 팀메이트에 프로젝트별 지침을 제공하세요.

## 11. 이 프로젝트(homepageDev)에서의 활용 아이디어

본 프로젝트는 노코드 웹빌더 플랫폼 개발 중이며, 다음 시나리오에 Agent Teams가 유용할 수 있습니다.

### 시나리오 1: 결제 플로우 통합 리뷰
```text
토스페이먼츠 실결제 연동 작업을 위한 팀을 만들어주세요:
- 1명: app/payment/card/page.js와 billing-auth route 보안 리뷰
- 1명: subscriptions/billing_history DB 스키마와의 정합성 검토
- 1명: MOCK_MODE 제거 후 실결제 전환 시 영향 범위 분석
```

### 시나리오 2: 플로우별 E2E 검증
```text
고객 플로우 루트 A(고객 직접) 전체 검증 팀을 만들어주세요:
- 1명: 가입→템플릿 선택→에디터 편집 경로 테스트
- 1명: 배포→trial 자동 생성→D-day 표시 검증
- 1명: 카드 등록→subscriptions.status='active' 전환 로직 검토
```

### 시나리오 3: 관리자/고객 화면 병렬 개발
```text
지원 티켓(support_tickets) 기능 개선 팀:
- 1명: /app/platform 관리자 콘솔 수정요청 탭
- 1명: /app/my/[subdomain] 고객 포털 수정요청/요청현황 탭
- 1명: DB 쿼리와 deadline_at 트리거 검증
```

→ 각 팀메이트가 서로 다른 파일 세트를 담당하므로 **파일 충돌 위험이 낮습니다**.

### 주의사항
- 현재 Windows 환경이므로 **in-process 모드 사용 권장** (`.claude.json` 또는 `--teammate-mode in-process`)
- 실험 기능이므로 중요 작업은 **git commit 자주 하며** 진행
- 세션 재개가 안 되는 한계가 있으므로 **짧고 목표가 명확한 작업**부터 시도
