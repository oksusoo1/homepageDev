# 작업 지시: 보안 구조 전환 ①단계 — 서버 뼈대 + 본사 콘솔 서버화

## 배경
현재 모든 화면이 브라우저에서 anon 키로 Supabase를 직접 읽고 쓰며, RLS는 전 테이블 USING(true)다.
권한 체크(isPlatformAdmin, 소유자 체크)가 브라우저에만 있어 우회 가능하다.
전체 계획은 ①서버 뼈대+본사 콘솔 → ②결제·상태 전환 → ③사장님 편집 → ④방문자 공개범위 → ⑤RLS 잠금.
이번 작업은 ①만 한다.

## 목표
1. 서버에서 "누가 요청했는지" 알 수 있게 세션을 쿠키 기반으로 전환
2. 서버 전용 DB 클라이언트와 권한 검사 공용 함수 준비
3. /platform(본사 콘솔)의 모든 DB 조회·쓰기를 서버(Server Actions)로 이동

## 사전 사항
- `.env.local`에 `SUPABASE_SERVICE_ROLE_KEY`가 이미 추가되어 있다.
  값은 Supabase 신규 형식 secret 키(`sb_secret_...`)다. 기존 브라우저용 키는 그대로 둔다.
- 신규 형식 키 인식을 위해 `@supabase/supabase-js`를 최신 버전으로 올릴 것

## 작업 내용

### 1. 세션 쿠키 전환
- `@supabase/ssr` 도입
- `lib/supabase.js`: `createBrowserClient`로 교체. export 이름(`supabase`)과 사용법은 유지해서
  기존 화면 코드가 그대로 동작해야 함
- `lib/supabase/server.js` 신규: `createServerClient` + `next/headers` cookies. 요청자 세션 확인용
- `proxy.js`: 기존 서브도메인 rewrite 로직은 그대로 두고, 세션 쿠키 갱신 처리만 추가
  (rewrite 동작이 바뀌면 안 됨)

### 2. 서버 전용 DB 클라이언트
- `lib/supabase/admin.js` 신규: `SUPABASE_SERVICE_ROLE_KEY`로 생성, 파일 첫 줄 `import 'server-only'`
- 이 키는 절대 `NEXT_PUBLIC_` 접두어 금지, 클라이언트 컴포넌트에서 import 금지
- `.env.local.example`에 키 이름만 추가 (값은 넣지 않음)

### 3. 서버 권한 검사 함수 — `lib/server/guard.js` 신규
- `getServerUser()`: 쿠키 세션으로 auth user 확인 (없으면 null)
- `requireStaff(roles = ['platform_admin'])`: staff 테이블에서 auth_id·status=active·role 확인.
  실패 시 에러 반환
- `requireSiteOwner(siteId)`: 요청자의 customer_id가 sites.customer_id와 같은지 확인
  (이번 단계에선 만들어만 두고 ②③단계에서 사용)
- 모두 `import 'server-only'`

### 4. /platform 서버화
- `app/platform/layout.js`(서버 컴포넌트) 신규 또는 수정: `requireStaff()` 실패 시 `/login`으로 redirect.
  브라우저 쪽 권한 체크는 화면 표시용으로 남겨도 되지만 실제 차단은 여기서 한다
- `app/platform/actions.js`('use server') 신규: /platform과 `components/Platform*`에서
  `supabase.from(...)`으로 하던 **조회와 insert/update/delete/upsert 전부**를 Server Action으로 이동
  - 예: fetchAll(전체 조회), createSite, updateSiteStatus, saveDevFee, 선금/잔금 확인,
    견적 진행, 1회성 결제 납부확인, 청구 납부확인, 고객요청 처리시작/답변완료, 사이트 수정/삭제,
    공통코드 편집, 개발>테스트의 청구 배치 실행
  - 목록은 예시이므로 코드를 검색해 빠짐없이 옮길 것
- 모든 Action 첫 줄에서 `requireStaff()` 호출 후, DB 작업은 `lib/supabase/admin.js`로 수행
- 반환 형식 통일: `{ ok: true, data }` 또는 `{ ok: false, error: '사용자용 메시지' }`. 클라이언트로 throw 금지
- 작업 후 /platform 관련 파일에 `supabase.from(` 직접 호출이 0건이어야 함

### 5. 옮기면서 고칠 버그 1건 (이것 외 동작 변경 금지)
- 본사 `updateSiteStatus('trial')`는 next_billing_date를 "체험 종료일 + 1개월"로 넣고,
  `lib/deploy.js`는 "체험 종료일"로 넣어 불일치
- `lib/deploy.js` 기준(체험 종료일)으로 통일. 체험 시작 계산은 공용 함수 하나로 만들어 양쪽이 같이 쓰게 할 것

## 하지 말 것
- /my, /s/**, /setup, /templates 화면의 DB 접근 방식 변경 (②③④단계)
- RLS 정책 변경 (⑤단계)

# 작업 지시: 보안 구조 전환 ②단계 — 고객의 결제·상태 전환 서버화

## 배경
①단계에서 서버 뼈대(lib/supabase/server.js, admin.js, lib/server/guard.js)와 /platform 서버화를 완료했다.
②단계는 사장님(고객)이 하는 작업 중 **돈과 sites.status가 바뀌는 것**을 서버로 옮긴다.
단순 편집(에디터 저장, 사이트 정보 수정, 사이트 생성, 게시판, 본사 요청 작성)은 ③단계이므로 이번엔 건드리지 않는다.

## 대원칙 (모든 Action 공통)
- 고객 식별은 반드시 쿠키 세션으로 서버에서 한다. 클라이언트가 보낸 customerId는 절대 신뢰하지 않는다
- 사이트는 클라이언트에서 subdomain(siteCode)만 받고, 서버가 조회 후 `requireSiteOwner()`로 소유권 확인
- 금액은 클라이언트 값이 아니라 DB(subscriptions.amount, one_time_payments.amount 등)에서 읽는다
- 현재 sites.status에서 허용된 전환인지 서버에서 검사하고, 아니면 `{ ok:false, error }` 반환
- DB 작업은 `lib/supabase/admin.js`, 반환 형식은 ①과 동일 (`{ ok, data }` / `{ ok:false, error }`)
- 파일 위치: 사이트 단위 작업은 `app/s/[siteCode]/admin/actions.js`, /my 작업은 `app/my/actions.js`

## 이번에 확정된 정책
1. **카드 등록 시 결제 시점**: 체험 전·체험 중 등록이면 결제하지 않는다(체험 종료일에 청구 배치가 첫 결제).
   해지 후 재구독(구독 cancelled 또는 site suspended)일 때만 등록 즉시 1개월분 결제
2. **셀프 사이트는 preview(검토) 단계 없음**: 셀프 흐름 = building → pay_method → trial → subscribed (→ suspended)
3. **카드는 고객당 1장**: 새 카드 등록 시 해당 고객의 기존 카드 비활성화 (현재 동작 유지)

  `docs/db/sql/migrations/027_self_no_preview.sql`
  → build_type='self' AND status='preview' 인 사이트를 'building'으로
- `docs/플로우.md` 셀프 흐름 표·다이어그램 수정

# 작업 지시: E2E 자동 테스트 구축 (Playwright)

## 목적
보안 구조 전환(①~⑤단계)을 진행하는 동안, 매 단계 후 명령 한 줄로 핵심 시나리오를 검증하고
단계별 캡처가 포함된 결과 문서를 자동 생성한다. 이후 모든 개발에서 회귀 테스트로 계속 쓴다.

## 환경
- 대상: 로컬 `http://localhost:3000` (환경변수 `E2E_BASE_URL`로 변경 가능)
- 서버는 이미 PM2로 떠 있을 수 있으므로 Playwright webServer는 `reuseExistingServer: true`
- `.env.local` 사용 키: `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `E2E_PASSWORD`(사용자가 추가함)
- 브라우저: chromium만

## 테스트 데이터 규칙
- 모든 테스트 데이터는 `e2e-` 접두어: 이메일 `e2e-staff@test.local`, `e2e-a@test.local`, `e2e-b@test.local`,
  사이트 주소 `e2e-{시나리오}-{실행시각}` (실행마다 고유해야 subdomain UNIQUE 충돌 없음)
- global-setup: 위 3개 계정이 없으면 auth admin API로 생성(비밀번호 `E2E_PASSWORD`),
  customers 행 생성, e2e-staff는 staff 테이블에 platform_admin으로 등록
- `test:e2e:clean`: `e2e-` 접두어 데이터를 FK 순서대로 삭제 (billing_history → subscriptions →
  one_time_payments → support_tickets → user_comments → user_posts → user_boards → sites → inquiries).
  계정 3개는 남긴다. 실제 고객 데이터는 절대 건드리지 않도록 접두어 조건을 반드시 건다

# 방문자(손님) 회원 설계

상태: 설계 확정, 구현 전 (보안 전환 ⑤단계 이후 진행)

## 1. 목적
가게 사이트(예: 마곡카페)의 손님이 그 사이트에 가입·로그인해서
문의·비밀글 작성, 본인 비밀글 열람을 할 수 있게 한다. 아임웹의 사이트별 회원과 같은 개념.

## 2. 사용자 구분
| 사람 | 플랫폼 | 가게 사이트 |
|---|---|---|
| 사장님 | customers (구독 고객) | 소유자 — 비밀글 전체 열람, 공지 작성 |
| 손님 | 없음 | 회원 (user_members) |
| 다른 가게 사장님이 가입 | customers (자기 가게) | 회원 |
| 본사 직원 | staff | 열람만 |

## 3. 구조
- 로그인 계정: Supabase Auth 하나 (통합 계정)
- 사이트별 가입 기록: `user_members` 테이블 1개, site_id로 구분 (사이트별 테이블 생성 금지)
- 소유자는 user_members에 저장하지 않는다. `sites.customer_id`가 단일 기준.
  회원 목록 화면에서 user_members + 소유자를 합쳐 "소유자" 배지로 표시

### user_members (안)
| 컬럼 | 의미 |
|---|---|
| user_member_id | PK |
| site_id | → sites |
| auth_id | → auth.users |
| name | 이름(닉네임), 필수 |
| phone | 선택 |
| marketing_agreed_at | 마케팅 수신 동의 시각 (선택 동의) |
| privacy_agreed_at | 개인정보 수집·이용 동의 시각 (필수) |
| status | active / blocked / withdrawn |
| use_flag, created_at, updated_at | 공통 |
- UNIQUE (site_id, auth_id)

## 4. 로그인 입구
- 플랫폼 로그인 `/login`: 사장님·직원용 (현행)
- 가게 사이트 로그인 `/s/{siteCode}/login`, 가입 `/s/{siteCode}/join`: 손님용
- **손님 경로에서는 customers 행을 절대 생성하지 않는다** (현재 /login은 로그인 시 customers 자동 생성)
- 로그인 쿠키는 사이트(호스트)별로 분리하는 방향. 한 가게 로그인이 다른 가게·플랫폼 관리 화면에 이어지지 않게.
  커스텀 도메인은 원래 호스트별이므로 일관됨. 세부는 구현 시 확정

## 5. 가입
- 필수: 이메일, 비밀번호, 이름, 만 14세 이상 확인, 개인정보 수집·이용 동의
- 선택: 전화번호, 마케팅 수신 동의 (필수 동의와 분리)
- 이미 Supabase 계정이 있는 사람(다른 가게 회원·사장님)이 가입하면: 로그인 후 동의 → user_members 행만 추가
- 사이트별 개인정보처리방침 페이지 필요 (사장님=개인정보처리자, 플랫폼=수탁자). 문구는 구현 시 확인

## 6. 로그인 방식
- 1차: 이메일/비밀번호
- 2차: 카카오 (카카오 비즈앱 전환 후. 사이트 주소별 리다이렉트 등록 관리 필요)
- 네이버: 미정 (Supabase 기본 미지원)

## 7. 사장님 회원 관리
- 1차: 회원 목록, 검색, 차단(status=blocked)
- 나중: 엑셀 내보내기 (개인정보 반출 기능이라 신중히)

## 8. 탈퇴
- 사이트 단위: 해당 사이트 user_members만 withdrawn. Supabase 계정은 다른 사이트 가입이 있을 수 있어 유지

## 9. 비밀글 연동
- user_posts에 작성자 계정 컬럼(보안 전환 ④단계에서 추가) 사용
- 열람: 사장님 전체 / 로그인 작성자 본인 / 그 외 "비밀글입니다"
- 비로그인 작성 비밀글은 사장님만 열람

## 10. 구현 시 결정할 것
- 로그인 쿠키 범위 최종 확정
- 차단된 회원의 기존 글 처리
- 개인정보처리방침 문구·동의 기록 보관 방식
